# Checkout UI/UX Audit

Audit date: 2026-08-06. Diagnosis only — no files were edited as part of this pass.

> Historical audit snapshot. Its provider names and implementation recommendations describe the retired checkout stack. The current provider/environment contract is documented in `woopayments-environment-architecture.md`.

## Executive Summary

The complexity is **self-inflicted, not inherent**. Theming a WooCommerce Checkout Block + Stripe Elements combination is genuinely fiddly, but this codebase's specific failure is architectural: a single client-side script (`checkout.js`) is reverse-engineering WooCommerce Blocks' internal DOM shape via CSS-class heuristics to build a custom three-screen wizard on top of markup it does not control and cannot get a stable contract from — and the project's own changelog (`docs/checkout/checkout-ui-architecture.md`, "Redesign v1" through "v16") shows that heuristic breaking and being re-patched at least five separate times (v2→v4→v5→v7 alone), plus a payment-blocking bug (v6), a data-desync bug that broke Stripe payment confirmation outright (v15), and two "unconfirmed live" patches shipped against production without verification (v16, and the still-open shipping-rate issue). This is the classic "layering mismatch" failure mode: presentation code trying to own state (which screen is showing, which fields belong to which "step") that only WooCommerce Blocks' own DOM/data model actually owns, with no supported extension point for it. The Stripe boundary itself, by contrast, is handled close to correctly (Appearance API only, `wc_stripe_get_element_options`, no iframe reach-in). Headline recommendation: keep the WooCommerce Checkout Block + Stripe Elements boundary exactly as-is, kill the from-scratch DOM-classification wizard in `checkout.js`, and replace the "three fake screens" UX with either (a) plain single-column checkout restyled through Blocks' own supported style surface, or (b) if a stepped feel is still wanted, a rebuild using WooCommerce Blocks' actual extensibility API (`registerCheckoutFilters`, `ExperimentalOrderMeta`/inner-block slots, ` @woocommerce/blocks-checkout` filter registry) instead of classifying and hiding Woo's own opaque DOM.

- `assets/checkout/checkout.css` — ~1120 lines. Single mobile-first stylesheet restyling native Woo Blocks class names plus the wizard chrome it builds.
- `assets/checkout/checkout-desktop.css` — ~220 lines, `min-width: 1024px`-gated, targets `.wc-block-components-sidebar-layout` for the two-column desktop split.

## Render/Control Chain

1. React `/checkout` handoff (state machine only) → full-document `/checkout/` load.
2. `native-checkout.php` — DTB's own thin shell + branded header. **DTB-owned, correctly scoped.**
3. WordPress loads the assigned WooCommerce Checkout page → **WooCommerce Blocks styling surface** (published, semi-stable class names like `.wc-block-checkout__contact-fields`, `.wc-block-components-checkout-step`).
4. `checkout.css` restyles that DOM by class name only — **supported surface, correctly used**, modulo the `!important` escalations noted below.
5. `checkout.js` runs on top of the *same* DOM and does two things:
   - a. **Classifies and hides/shows Woo's own opaque step wrappers** to fake a 3-screen wizard — **unsupported surface**, this is DOM archaeology, not an API.
   - b. **Writes into `wc/store/cart`'s public dispatch actions** (`setBillingAddress`/`setShippingAddress`) — this part *is* a supported, documented extensibility point (WooCommerce Blocks' public data store), used correctly, but it exists only to compensate for gap 5a/CheckoutFieldPolicy's dual-field-group design (see Finding 2).
6. Stripe's Payment Element mounts inside `stripe_upm`'s iframe, styled exclusively via `StripeElementAppearance.php`'s Appearance API — **correct, supported, boundary-respected.**
7. `checkout-desktop.css` re-lays the same DOM at ≥1024px via `.wc-block-components-sidebar-layout`, WooCommerce's own published two-column region — **supported surface**, with one documented `!important` needed because Woo's own flex rule has equal specificity and no theme-provided container-query ancestor exists to activate Woo's native responsive split.

## Root Cause Findings (ranked by impact)

### 1. Layering mismatch — a hand-rolled wizard classifying WooCommerce Blocks' private DOM shape (highest impact)

`checkout.js` `classifyStepGroups()` (lines 147–199) buckets Woo's own step cards into Contact/Shipping/Payment by matching a list of CSS classes (`GROUP_DEFINITIONS`, lines 103–124) and falling back to "whichever step precedes it in document order" for anything unmatched. This is not a documented WooCommerce Blocks extension point — it is pattern-matching against implementation-detail class names, with three fallback layers (semantic class match → nearest `.wc-block-components-checkout-step` ancestor → previous-sibling bucket-of-last-resort) because there is no real contract to hang a "step" concept off. The project's own changelog documents this heuristic being fully rewritten three times:
- v2 shipped keyed on `data-block-name`, which the doc says "returns an empty array for every step" in production (never emitted outside the block editor).
- v4 replaced it with DOM-position/ordinal inference (`first/last .wc-block-components-checkout-step`), which the v5 entry says "did not reliably separate Shipping from Payment on this store's actual rendered markup."
- v5 replaced it again with the current semantic-class approach, which itself needed a v7 patch because an unclassified "Shipping options" placeholder card "leaked" onto the Contact screen.
- v6 shows a related bug where a *global* validation selector (`wc/store/validation`'s `hasValidationErrors()`) permanently blocked "Continue" because it isn't scoped to a step — evidence that the wizard's step boundary is a UI fiction the underlying Woo validation model has no concept of.

This is Cause 1 from the design-system skill's framework almost verbatim: "presentation code trying to control state that a third-party system already owns, requiring workarounds instead of direct control." Every regression above is the direct, repeated cost of that mismatch, not incidental bugs.

### 2. Duplicate identity/state, papered over with a live client-side sync (high impact, and the one true correctness bug found)

`CheckoutFieldPolicy.php` deliberately creates a second, parallel field group (`dtb/first_name`/`dtb/last_name` via Additional Checkout Fields) instead of using WooCommerce's own canonical `billing_first_name`/`shipping_first_name`, because a wizard "Contact" step wants name collected before address. This is defensible on its own, but it means the customer's name now lives in two different state trees that must be kept in sync: a server-side sync at order-processing time (correct, and necessary), and — because Stripe's Payment Element and the Shipping-step Address Element both read `billing_details.name`/shipping name from the **client-side** `wc/store/cart` store, not from Woo's Additional Checkout Fields — a second, hand-written client-side sync in `checkout.js` (`syncContactIdentityToAddresses()`, lines 357–396) using debounce, blur (capture-phase, since blur doesn't bubble), two post-hydration timer passes, and a `wp.data.subscribe()` re-assertion to fight a "server-driven cart refresh... can race ahead of this file's own dispatch." Per the changelog (v15), the *absence* of this client sync **broke live Stripe payment confirmation outright** ("Missing required param: payment_method_data[billing_details][name]") — this was not a cosmetic bug, it was a checkout-blocking production incident caused directly by the two-field-group design. This is the clearest evidence in the whole audit that a "one checkout field set, one payment state" violation (which `AGENTS.md`/the commerce-checkout contract explicitly requires) produced a real functional failure, not just messy CSS.

### 3. Legacy/superseded CSS layers, partially but not fully cleaned up (medium impact)

`checkout-ui-architecture.md` documents an entire prior presentation stack (`checkout-flow.css`, `checkout-boot.js`, `checkout-ui.js`, `checkout-express-entry.js`, `applepay.php`) that was deleted in a 2026-07-28 reset specifically because it was "competing CSS and JavaScript layers." That cleanup was real and is good evidence the team already recognizes this pattern as a problem once before. However, `checkout.css` itself still carries an internal fossil: section 5b is a no-op comment block ("Superseded by checkout-desktop.css... This block used to duplicate that grid on a different element at the same breakpoint — the two fought each other") describing a bug that was fixed by adding an *entirely separate* file (`checkout-desktop.css`) rather than removing the dead code from `checkout.css`. It's harmless today (empty), but it's a second file now needed to reason about one breakpoint's layout, and the note describing why is itself evidence of exactly the "two layout authorities fighting" pattern recurring within the same file's history.

`!important` usage has grown past the "one documented provider-compatibility case" the entry criteria promise in `checkout-ui-architecture.md` (step 4): there are now at least four separate `!important` escalations across `checkout.css`/`checkout-desktop.css` — the accordion-radius case (documented), the shipping-radio-position case (documented, v11), `.screen-reader-text`/visually-hidden (v6/v13, justified as accessibility not compatibility), and the desktop `.wc-block-components-sidebar-layout` grid override (documented, but is a second CSS-specificity war, this time against Woo's own container-query-gated flex/grid split). None of these are individually unreasonable, but their accumulation is a symptom of fighting Woo's own cascade rather than layering cleanly on top of it, exactly Cause 4 in the skill's framework applied to layout, not just to the Stripe iframe.

### 4. Not found: iframe reach-in, duplicate form fields/validation, or step-forked business logic

Explicitly checked and **cleared**:
- **Stripe iframe boundary**: `StripeElementAppearance.php` only uses the documented `wc_stripe_get_element_options` filter and Appearance API `variables`/`rules`/`theme`; `checkout.css` explicitly limits itself to "container chrome only" and its own header comment states it "never reaches into a Stripe Elements/Payment Element iframe." No CSS selector in either file targets an iframe or attempts to pierce it. This boundary is respected correctly.
- **Duplicate/custom form fields**: the wizard does not clone fields (confirmed against the doc's explicit "never creates, clones, duplicates, or moves a native field" claim, and against `checkout.js`'s actual code — it only toggles `display`/`inert` on Woo's own nodes). The one genuinely duplicate *state* (not field) is the Contact-name issue in Finding 2 above, which is a real problem, but it is not a cloned DOM control.
- **Step-forked business logic**: `checkout.js`'s `STEPS`/`isMobile()` gate is presentation-only — at `≥768px` the wizard chrome doesn't mount at all and `clearVisibility()` runs, leaving the plain single-scroll Woo Blocks form as the actual checkout logic path; there is one checkout field set and one submission button (Woo's native "Place order," explicitly never duplicated — `wizard.continueBtn.hidden = onPaymentStep`). This part of the architecture contract is honored.

### 5. Process risk compounding the technical risk (contextual, not a code defect)

Two entries in the changelog (`v16`, and the still-"Known open issue" shipping-rate entry) are explicitly flagged as **shipped to production without live verification**, blocked by SiteGround's bot/WAF layer returning captcha challenges to both scripted and headless-browser verification attempts from the working environment. Combined with the DOM-classification fragility in Finding 1, this means the riskiest part of the stack (a heuristic against markup the team cannot reliably automate-verify) is also the part most often shipped unverified. This is an operational amplifier of Finding 1, not a separate root cause, but it explains why the same class of bug keeps recurring rather than being caught before deploy.

## Rebuild vs. Refactor Recommendation

**Verdict: targeted rebuild of the wizard/interaction layer, not a full rebuild.** The CSS restyling layer (`checkout.css` sections 1–17, `checkout-desktop.css`) is fundamentally sound — it targets Woo Blocks' own published class names, uses the Stripe Appearance API correctly, and its `!important` usage, while creeping, is each individually justified against a real cascade conflict. Do not rebuild that. The actual defect is narrowly `checkout.js`'s DOM-classification wizard plus the identity-field split it's compensating for.

**Remove/replace:**
1. `assets/checkout/checkout.js`'s `classifyStepGroups()`/`GROUP_DEFINITIONS`/`applyVisibility()`/wizard-chrome machinery (roughly lines 91–724). This is the component that has been rewritten three times in-repo and still requires a documented "fails safe to plain single-scroll checkout" escape hatch (`reconcile()`, lines 684–714) because it cannot guarantee it will keep working against Woo Blocks version changes. Rebuilding it a fourth time on the same premise (pattern-matching Woo's opaque DOM) will not fix the underlying problem — it needs a different premise.
2. `CheckoutFieldPolicy.php`'s dual-field-group design (`dtb/first_name`/`dtb/last_name` as an extra Additional Checkout Field group, plus the client-side sync it requires in `checkout.js`) — replace with using WooCommerce's own canonical `billing_first_name`/`shipping_first_name` directly as the "Contact" identity fields, reordered/restyled via Blocks' own field-order and step-grouping *filters* (WooCommerce Blocks' `additional-checkout-fields` and the checkout step's inner-block ordering are editor-configurable — verify current block-editor step/field order before assuming code has to own it) instead of hiding native fields and re-deriving them. This removes both the sync bug class from Finding 2 and the "phone asked twice" operational footgun already documented in the architecture doc.

**What the "correct approach" looks like**, per what's already used correctly elsewhere in this same codebase and confirmed against the docs:
- Presentation stays exactly as it is today: CSS against Woo Blocks' published class names (`checkout.css`, `checkout-desktop.css`) — proven, keep it.
- Stripe styling stays exactly as it is today: `wc_stripe_get_element_options` + Appearance API (`StripeElementAppearance.php`) — proven, keep it.
- Order-summary customization stays exactly as it is today: the documented `itemName` filter via `window.wc.blocksCheckout.registerCheckoutFilters` (`checkout-order-summary.js`) — proven, keep it, and treat it as the template for how any further per-field customization should be done (a registered filter, not a DOM classifier).
- For the "does it feel like distinct steps" goal: either (a) drop the fake wizard and ship the single-scroll, well-styled Checkout Block WooCommerce already renders — collapsible per-section cards are already native Blocks behavior (`.wc-block-components-checkout-step--disabled` collapse-to-summary, already used and styled in `checkout.css` section 5) and may satisfy the "feels progressive" goal with zero custom JS; or (b) if a true wizard is a hard product requirement, it must be built from WooCommerce Blocks' actual public extensibility surface (the checkout filter registry already proven in `checkout-order-summary.js`, plus `wc/store/checkout`'s documented step-navigation actions if/when Woo Blocks exposes one) rather than DOM classification — this needs a compatibility check against the currently-installed WooCommerce Blocks version's actual public API before committing to it, since the whole point is to stop guessing at Woo's internals.

**Phased approach if a wizard is kept as a requirement:**
- Phase 1 (low risk, immediate): remove the client-side identity sync workaround by switching Contact fields to canonical billing/shipping name fields (Finding 2's fix). This alone removes the highest-severity bug class (Stripe payment confirmation failure) independent of any wizard decision.
- Phase 2: replace the wizard with plain single-scroll + native collapsible steps; ship and validate on real WooCommerce Blocks-version staging (not blocked by SiteGround WAF — test pre-WAF or with an approved bypass) before any further "wizard" work is attempted, to establish a stable non-wizard baseline first.
- Phase 3 (only if product still wants a stepped UI after seeing Phase 2 live): scope a wizard against Woo Blocks' actual documented public API surface for the currently pinned WooCommerce/Blocks version, not DOM class names, with an explicit compatibility test in CI/staging against WooCommerce version bumps so a future Woo update can't silently break step classification again the way it has three times already.

## What Must Never Change

Restated from `AGENTS.md`/`docs/checkout/checkout-ui-architecture.md`, unaffected by any of the above:

- WooCommerce Checkout Block remains the only order-creation surface; Payment Plugins for Stripe (`stripe_upm`) remains the only card/wallet payment authority. Neither React nor DTB theme/MU-plugin code may create PaymentIntents, Checkout Sessions, payment fields, wallet tokens, or captures.
- Stripe Elements/Payment Element iframe contents are styled only through the Stripe Appearance API (`wc_stripe_get_element_options`) — never inspected, cloned, or mutated. `StripeElementAppearance.php` is the correct pattern; any rebuild must keep using exactly this mechanism.
- WooCommerce owns cart/session state, canonical contact/address fields, shipping, tax, discounts, totals, Checkout Block validation, order creation, and order/payment status. A rebuild that removes the wizard must not accidentally start writing checkout business state (validation, totals, eligibility) into DTB code — only presentation and the documented filter/data-store touchpoints already proven safe (`itemName` filter, `setBillingAddress`/`setShippingAddress` dispatch) are in bounds.
- One checkout field set, one payment state, one native order-submission action — this must survive any rebuild exactly as it does today (Woo's native "Place order" button, never duplicated).
- Order identity/contract meta (`_dtb_checkout_gateway`, `_dtb_checkout_contract_version`, `_dtb_payment_provider`, captured-payment gating) is entirely unaffected by this presentation-layer audit and out of scope for any UI rebuild — do not touch it as part of this work.
- Checkout, order-pay, callback, and payment endpoints remain private/non-cacheable; script/style enqueue order relative to WooCommerce/provider handles must stay deterministic (`dtb-checkout` priority 30, `dtb-checkout-desktop` depending on `dtb-checkout`) in any rebuild.
