## Executive assessment

DTB already contains a substantial marketplace backend, including shared channel/order/message/event/exception/audit persistence, admin REST surfaces, credential storage, an eBay OAuth token service, a Sell Fulfillment API client, order import, tracking submission, message handling, and eBay account-deletion notification handling. The active load list is in `dtb-integrations/bootstrap.php`.

The production site currently reports the eBay integration as unconfigured, so it is not connected. eBay orders now have a deployed signed `ORDER_CONFIRMATION` notification consumer feeding Action Scheduler and the existing order-import/materialization path; the hourly poll remains reconciliation. This is a source-level path only: the eBay destination and user subscription are not configured, seller consent is absent, and no live notification or order readback proves real-time sync. Message polling remains twice daily and its discovery/send path is not demonstrated. Tracking sync is scheduled hourly but the queue handler only dispatches extension hooks; no concrete eBay shipment-selection/projector was found in the inspected active path. The eBay adapter has no listing/inventory synchronization implementation. The seller's eBay Developer/Seller Hub state, consented scopes, successful job execution, and eBay-to-Veeqo channel mapping remain unverified. The latest live Veeqo read shows Veeqo is configured, but its inventory projection is stale and its webhook verification is disabled.

At the initial audit snapshot, the deployed public eBay account-deletion webhook accepted anonymous POSTs and could redact conversations from unverified body data. That source-level vulnerability was addressed by the 2026-11-23 MCP DTB deployment: the active path now invokes the eBay signature verifier, validates topic and nested identity, queues an HMAC buyer reference, and applies notification/action duplicate containment. The fix has not been behaviorally exercised in production or independently reviewed; deletion coverage remains incomplete beyond conversations/messages. A centralized materialization-gate check and failed-run watermark correction were also deployed. The eBay account is still unconfigured and the eBay/Veeqo channel relationship remains unverified.

## Findings

### High: first-import materialization bypassed the declared feature gate (source fix deployed; behavior not independently verified)

`MarketplaceMaterializationQueue.php` defines `DTB_MARKETPLACE_MATERIALIZATION_ENABLED` as `false` by default and guards its scheduled recovery path. Previously, `EbayFulfillmentService::sync()` called `materialize_ebay()` for newly imported orders and `OrderMaterializationService::materialize()` did not enforce the gate. The deployed change checks the shared gate in the materialization service before Woo order creation, returning `disabled` when the gate is absent or false; this also applies to Amazon calls through the shared service. Production file readback confirms deployment, but behavior under enabled/disabled modes, all caller paths, and Veeqo duplicate-ingress conditions still requires tests and review.

### High: the order poller could move past failed work (source fix deployed; cursor semantics still need verification)

Previously, `EbayFulfillmentService::sync()` broke on failed API pages but still advanced `dtb_ebay_last_order_sync` and appended `EVT_SYNC_SUCCEEDED`; per-order exceptions were counted but did not prevent the watermark advance. The deployed correction records `EVT_SYNC_FAILED` and leaves the prior watermark unchanged after page/import failures. A subsequent deployment bounded each worker to one 200-order page and queued fixed-window offset continuations; the watermark advances only when the final page succeeds. The seven-day bootstrap ceiling remains, as do mutable-offset pagination risk, provider retention uncertainty, and unverified queue/runtime recovery. Re-readback of the final service write and post-write health checks are still pending because MCP DTB began returning `invalid_mcp_response` immediately after its write receipt.

### High: “connected/synchronized in real time” is not demonstrated

The active job schedule uses WordPress cron: eBay orders hourly, eBay conversations twice daily, tracking hourly, health twice daily. A signed `ORDER_CONFIRMATION` notification receiver is now deployed at `/wp-json/dtb/v1/marketplace/ebay/deletion`; it queues a bounded single-order sync and retains hourly polling reconciliation. However, the eBay notification destination/subscription is not configured, the seller has not granted the required scopes, and no delivery, queue completion, or order readback was observed. The inspected tracking job only calls `do_action()` extension hooks. The current twice-daily inbox job is also not a working Message API poller: it reads only local open conversations, passes an empty buyer username, and calls the legacy Post-Order inquiry endpoint. General Site Health scheduling status does not attest to marketplace hooks or freshness. Define a measurable latency target and prove notification-to-readback timing before claiming near-real-time operation.

### High: single order-ingress authority is unresolved

The active source clarifies the DTB/Veeqo direction. Marketplace materialization creates a WooCommerce order and enqueues the Woo order-platform Veeqo job. `Veeqo/VeeqoClient.php` sends a Woo order to Veeqo `POST /orders` using its configured, verified Direct channel; the request uses `channel_order_number` as the provider idempotency key. The signed Veeqo `order.status_changed` webhook in `OperationalPipeline/VeeqoWebhookPipelineController.php` resolves an already-existing Woo order by Veeqo ID or channel order number; if no Woo order resolves, it quarantines the event for operator reconciliation and does not create a Woo order. Thus no Veeqo-to-Woo eBay sale creation path was found in the active DTB source. The Veeqo integration README likewise distinguishes Direct order-export eligibility from a WooCommerce-type channel and says discovery alone is not order-export authorization. However, the seller may independently have eBay connected in Veeqo and importing the same sale there; current Veeqo provider channel evidence remains unavailable because the MCP connection requires reauthentication. Keep the Woo materialization gate disabled until live Veeqo eBay channel state, Veeqo's seller-side order import behavior, the DTB Direct channel and all external IDs are verified. Then choose a single ingress: eBay->DTB/Woo->Veeqo or another explicitly supported owner path, and prove duplicate containment and stable identity before activation.

### High: targeted notification retry is implemented; runtime recovery remains unverified

The initial deployment lost the notification's order ID at its exception boundary. The 2026-11-23 refinement now retains the exact ID in exception context, deduplicates the open record by that identity, retries through the single-order hook, and resolves the exception after successful sync. Guarded production write and readback hashes are recorded above. This closes the source-level identity-loss defect; retry scheduling, eventual success resolution, retry exhaustion, concurrent duplicate jobs, terminal failure handling, and operator readback remain runtime-unverified. Keep the finding high until those failure/recovery states are independently reviewed and exercised.

### Critical: marketplace-to-Woo order creation remains disabled

The production `MarketplaceMaterializationQueue.php` readback confirms `DTB_MARKETPLACE_MATERIALIZATION_ENABLED` defaults to `false`; the materialization service checks this gate before calling `wc_create_order()`. This correctly avoids duplicate order creation while eBay direct import versus Veeqo channel ingestion is unresolved, but it also means a successful eBay read/notification does not by itself create or synchronize a WooCommerce order. The setting must not be enabled merely to make the requested connection appear functional. First verify which path owns the sale, stable order identity, how Veeqo ingestion behaves, and how downstream Veeqo/QuickBooks jobs are triggered; then define a bounded approved rollout and prove duplicate containment before enabling Woo order materialization.

### Medium: current notification wiring covers order confirmation only

The deployed consumer recognizes `ORDER_CONFIRMATION`; it acknowledges other authenticated topics without action. Current eBay topic documentation also describes order cancellation and return activity notifications, each with distinct authorization scopes. The configured OAuth scopes do not request those cancellation/return scopes. This may be correct for an initial purchase-only rollout, but cancellation/return/refund state is not event-connected by the new receiver. Decide in scope whether those lifecycle events are required; if so, add topic-specific payload validation, least-privilege consent, domain-owned workflows, and idempotent handling. Do not request those scopes or claim lifecycle coverage until that decision and source path are reviewed. eBay documents `ORDER_CONFIRMATION` as a post-checkout, payment-cleared event with HTTPS delivery and the two `sell.fulfillment` scopes; it separately defines `ORDER_CANCELLATION_ACTIVITY` and `ORDER_RETURN_ACTIVITY` with their own scope pairs. [eBay Notification Topics](https://developer.ebay.com/develop/api/sell/notification_events)

### Medium: current eBay feature coverage is narrow

The inspected eBay adapter covers Fulfillment API order reads/shipment writes, Post-Order message operations, OAuth, health checks, and marketplace account-deletion notifications. No eBay Inventory API offer/listing, price, quantity, product/catalog publication, cancellation/refund, or returns synchronization implementation was found in the relevant `Ebay/` and Marketplace wiring. Veeqo may own channel listing operations separately; prove that path rather than treating existing eBay order connectivity as full catalog/store integration.

### High: eBay inbox sync has no conversation discovery path and calls legacy inquiry routes with missing identity

The active `dtb_ebay_message_sync` scheduled callback reads only already-existing open DTB conversations, then calls `DTB_EbayMessageService::sync_messages()` with the conversation's item ID and an explicitly empty buyer username. A repository-wide search found `DTB_MarketplaceReadModels::upsert_conversation()` only at its method definition; no active eBay caller creates/populates conversations. Therefore the scheduled poll has no demonstrated path to discover new eBay conversations and may have no rows to poll. The service issues `GET /post-order/v2/inquiry` with `item_id`, empty `buyer_username`, and status `OPEN`; eBay's official Post-Order API catalog documents inquiry search at `/post-order/v2/inquiry/search`. For general member conversations, the current Message API documents `GET /commerce/message/v1/conversation` with required `conversation_type` and `commerce.message` authorization scope, followed by `GET /conversation/{conversation_id}` for details. The OAuth URL and token refresh scope were updated to request `commerce.message`; the seller has not yet granted it. ### Critical: account-deletion workflow is only partially covered; deployed signature path and acknowledgement timing need independent verification

At the audit snapshot, the live handler trusted anonymous body data and lacked signature validation. The deployed replacement uses `EbayNotificationSignatureVerifier`, the eBay application-token/public-key endpoint, one-hour public-key cache, encrypted short-lived application-token cache (deployed follow-up above), ECDSA/SHA-1 verification per the official PHP SDK, nested `notification.data` identity, and Action Scheduler work keyed by derived HMAC buyer reference and notification identity. It returns 204 when already queued/completed or durably scheduled; invalid signatures return 412 and verification/queue failures fail closed. Production readback confirms source presence, not runtime behavior. Canonical serialization, current signature/key responses, OpenSSL availability in production, replay races, Action Scheduler persistence, and full deletion coverage remain unverified. **The provider contract is internally inconsistent:** eBay's current [account-deletion guide](https://developer.ebay.com/develop/guides/sell/marketplace-user-account-deletion) says immediately acknowledge, then verify, yet its verification section describes 412 on failed signature; the [official PHP SDK](https://github.com/eBay/event-notification-php-sdk) verifies in the request path and returns 412/204. The active callback verifies before durable enqueue/ack; a cold cache can still require up to two outbound calls with 8-second timeouts. The one-hour encrypted token cache optimization removes a token round trip while warm but does not settle the response-order conflict or bound cold-path latency. Before subscription, obtain a provider-confirmed contract or reproduce the official test-notification behavior and document the decision. Preserve signature verification before identity lookup or effects; if adopting acknowledgement-before-verification, first persist a strictly bounded, encrypted, short-retention envelope and ensure every acknowledged event reaches terminal verification/processing or operator recovery. `redact_buyer()` also does not prove deletion/anonymization of marketplace order rows, Woo billing/shipping fields, or Veeqo/downstream copies. Do not subscribe/activate deletion notifications until full deletion coverage and end-to-end handling are proven. Historical unauthenticated endpoint exposure is mitigated by deployment, not retroactively erased.

The official [eBay PHP Event Notification SDK](https://github.com/eBay/event-notification-php-sdk) was inspected at commit `463a5cbc87141bc45f2f14984175603792242a38`. Its source/test fixture provides the signature shape and algorithm currently followed locally, but the repo also declares a full Slim/Guzzle/async dependency stack, has no visible time expiry on its LRU key cache, has questionable response-body handling, verifies `json_encode()` of the decoded PHP array, and has conflicting ISC Composer metadata versus Apache-2.0 source headers. Local code reuses the documented signature contract but replaces the SDK transport/cache. A security reviewer must validate eBay's canonicalization contract with official valid/invalid fixtures and resolve the dependency/license observations before approving this implementation.
